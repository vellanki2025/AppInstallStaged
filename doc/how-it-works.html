AppInstallStaged — How It Works

A system-privileged app that stages pre-downloaded, signed APKs for install on the next reboot.

In one sentence

Signed APK files are dropped into a known folder on the vehicle. When the app launches, it hands every APK in that folder to the Android PackageInstaller as a staged session, which the platform applies atomically on the next reboot — with no user prompts, because the app runs with system privilege.

The background assumptions

  • APKs are already downloaded. An upstream agent (OTA, fleet manager, USB load, provisioning service) fetches the packages and writes them into the drop folder. This app downloads nothing.
  • APKs are already signed and trusted. They are expected to be signed with a key the platform accepts (platform/OEM key). The app does not verify or re-sign; the framework enforces signatures at install time.
  • No runtime permissions are requested. The app is system-privileged and reads its own app-specific directory, so there are no user-facing permission dialogs. The privileged permissions are install-time grants, not prompts.

What a "staged" session is

A normal PackageInstaller session installs immediately. A session created with SessionParams.setStaged(true) is instead written to disk and committed to apply on the next reboot. This is the same mechanism Android uses for APEX modules and system updates: the package does not go live at runtime — it is verified, queued, and activated during a controlled boot. That is the right model for an Automotive image, where you want packages to land during a reboot rather than mutate a running system.

A successful commit means staged and verified, not installed yet. The app reports "Applies on next reboot" and offers a Reboot now button to trigger it.

The end-to-end flow

1

APKs land in the drop folder

Upstream process writes *.apk into /sdcard/Android/data/com.example.appinstall/files/staged-apks/.

2

App launches and scans

InstallActivity.onCreate() calls PackageInstallerHelper.listApks() to collect every APK, sorted by name.

3

A staged session is built

One APK → a single staged session. Several APKs → one multi-package staged parent with a child session per APK, so they apply together.

4

APK bytes are streamed in, then committed

Each APK is copied into the session via openWrite(); session.commit() fires with a status callback. With USER_ACTION_NOT_REQUIRED and system privilege, the commit is silent.

5

Status returns, then reboot applies

InstallResultReceiver receives STATUS_SUCCESS ("applies on next reboot"). On reboot the staged session activates and the packages are installed.

The drop folder

Default location (needs no storage permission, always readable by the app):

/sdcard/Android/data/com.example.appinstall/files/staged-apks/

Push one or more signed APKs there after the app is installed, then launch it (or tap Rescan folder):

adb push app1.apk /sdcard/Android/data/com.example.appinstall/files/staged-apks/
adb push app2.apk /sdcard/Android/data/com.example.appinstall/files/staged-apks/

To use a provisioned vendor path instead, set PackageInstallerHelper.apkDirOverride to an absolute path such as /data/vendor/appinstall/apks. That directory must already exist and be readable by the app's SELinux domain.

Why it needs system privilege

INSTALL_PACKAGES is a signature|privileged permission. It is granted only when the app is either signed with the platform key, or shipped in a privileged system partition (/system/priv-app or /product/priv-app) and whitelisted. Only then does the commit run silently. Without it the framework returns STATUS_PENDING_USER_ACTION and shows the install dialog — the app handles that case, but it is not the intended deployment.

Privileged permissions used

PermissionWhy
INSTALL_PACKAGESSilent install with no confirmation UI.
DELETE_PACKAGESSilently replace an existing package of the same name.
REBOOTTrigger the reboot that applies the staged session.
QUERY_ALL_PACKAGESInspect installed packages for status/verification.

Deploying as a privileged system app

# 1. Sign the release APK with the platform key (or let the ROM sign it).
# 2. Push it into the privileged partition:
adb root && adb remount
adb push app-release.apk /system/priv-app/AppInstall/AppInstall.apk

# 3. Install the privileged-permission whitelist:
adb push system/etc/permissions/privapp-permissions-com.example.appinstall.xml \
    /system/etc/permissions/

# 4. Reboot and confirm the grant:
adb reboot
adb shell dumpsys package com.example.appinstall | grep INSTALL_PACKAGES
On an enforcing build, a priv-app whose signature permissions are not whitelisted (step 3) can prevent the device from booting — by design.
